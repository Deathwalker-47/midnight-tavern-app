# High-Level Plan

A local-first roleplay application with gated, deterministic game mechanics and persistent, evolving memory. This document is a standalone architectural brief: it defines what the application is, how it is structured, what each part is responsible for, and what the first release includes. A separate low-level, step-by-step implementation plan will follow before development begins.

---

## 1. Overview

The application is a desktop-first (mobile-capable later) roleplay chat client. A user plays through an interactive story narrated by a large language model (LLM). Unlike typical roleplay clients where the model freely narrates outcomes, this application enforces **deterministic game mechanics** — dice rolls, skill gating, inventory, and resources are owned by the program, not the model. The model writes prose; the program decides what is mechanically true.

Alongside mechanics, the application maintains **persistent, evolving memory**: character sheets that grow as the story progresses, tracked relationships, a running plot summary, and world state. Memory keeps long stories coherent and lets characters visibly develop over time.

Everything runs **locally**. The user supplies their own model access (an API key). The application hosts no content and relays no model traffic through its own servers.

## 2. Goals and non-goals

**Goals**
- A roleplay experience where player actions have real, enforced consequences — capabilities and progression cannot be fabricated by the model.
- Characters and world state that persist and evolve coherently across long play sessions.
- Easy onboarding for newcomers, with deep configurability available for advanced users.
- A clean, local, low-overhead product with no server-side content hosting.

**Non-goals (explicitly out of scope)**
- No server-hosted inference or any system where the application relays model calls under its own account/key. Users bring their own model access.
- No in-application currency for purchasing model usage.
- No automated generation of images, comics, or video from the story.
- No hosted content marketplace. The application may fetch user-directed content; it does not curate or host a gallery.
- No semantic/vector search in the first release (see §11).

## 3. Design philosophy: rules that hold

The central promise is that **the world has rules even the narrator cannot break.** This is the differentiator and it drives every architectural decision.

The key insight: LLMs are unreliable as the authority over game state. They will grant abilities a player has not earned, fudge outcomes for drama, and drift from established facts over a long context. Attempts to fix this purely through prompting are unreliable — models inconsistently honor instructions delivered through system channels or message content. Approaches that delegate mechanical authority to a *second* model also fail, because two models can disagree and drift apart, producing incoherence.

The reliable solution is to make the **program**, not any model, the authority over mechanical state. The model is reduced to a prose renderer. Mechanical truth lives in program-owned state that the model cannot write, enforced by deterministic code. The model can *narrate* getting a sword; only the program can make it *true*.

## 4. Architecture principles

1. **Local tool, not a hosted service.** Nothing is hosted: no content storage, no relayed inference, no account-bound model key. This keeps the product a piece of software the user runs, not a platform the operator is responsible for.
2. **Single-language codebase, no internal network boundary.** The non-UI logic ("the core") and the UI share one codebase and pass data structures directly, with no HTTP layer between them.
3. **Separation of authoritative and observed state.** Mechanical state (the "ledger": resources, skills, inventory) and narrative state (personality, relationships, observations) live in **separate stores with separate writers**, joined only at render time. This separation is structural, not conventional: the narrative-extraction process has no reference to mechanical state and therefore cannot corrupt it.
4. **Generate-once, then freeze.** A story's rule set (its stats, skills, items, starting values) is generated by an LLM once at story creation, then **frozen** into a fixed configuration. During play, mechanics are enforced deterministically against the frozen rule set. The model never invents new mechanical content mid-story.
5. **Enforce by validation and ownership, not by trusting the model.** The program owns the request pipeline end to end. It computes mechanical outcomes itself, writes them to authoritative state directly, and re-supplies that authoritative state to the model each turn. The model's prose can never silently change what is mechanically true.

## 5. Technology stack

- **Language:** TypeScript for both core and UI (one codebase, shared types, no internal service boundary, and a path to both desktop and mobile from the same core).
- **UI:** A component-based UI layer (e.g. React for desktop shell, with React Native as the later mobile target).
- **Desktop shell:** An app shell that bundles the UI and core into an installable application (e.g. Tauri or Electron).
- **Storage:** Embedded SQLite for structured local persistence.
- **Model access:** Standard OpenAI-compatible HTTP requests to a user-configured endpoint (see §10).
- **No Python, no heavyweight ML runtime** in the core. Any future embedding capability uses in-process ONNX (e.g. transformers.js), not a separate Python service.

## 6. System architecture

The system has two layers in one codebase:

- **Core** — all non-UI logic: the mechanics engine, the memory system, the story bootstrapper, the model router, and the persistence layer.
- **UI** — all user-facing screens, which read core state and dispatch user actions.

State is divided into three categories:

1. **Frozen Story Schema** — the story's rule set, generated once and read-only during play.
2. **Hard State** — the authoritative mechanical ledger, per character. Sole writer: the mechanics engine.
3. **Soft State** — narrative/observed memory, per character and for the world. Sole writer: the memory analyzer.

Hard and Soft state are joined only when rendering a character view; nothing writes through that joined view.

## 7. Data model (high level)

### 7.1 Frozen Story Schema (read-only during play)
- **Stat mode:** one of `none`, `light`, or `full`. Some stories have no mechanical stats at all (e.g. pure social/intrigue); this is a first-class option, decided before any stats are defined.
- **Resources:** the numeric bars the story uses (e.g. health, stamina). Empty when stat mode is `none`. Each has an id, label, start value, max, and a visibility flag.
- **Skills:** the complete, closed set of learnable skills. Each has a description, a tier, prerequisites (conditions that must hold to learn it), and unlock paths (the only defined ways to acquire it). Optionally a **mastery model** (see §8.1).
- **Items:** the complete item/equipment table. Each has a kind, tier, optional skill requirement to use, and mechanical properties.
- **Tiers:** rarity/power tiers and where each may first legitimately appear (prevents implausible rewards).
- **Starting state:** what the player begins with (resource values, starting skills, starting inventory).

### 7.2 Hard State (authoritative ledger; written only by the mechanics engine)
- Per character: current resource values, the set of learned skills (with mastery if used), inventory, and progress flags.

### 7.3 Soft State (observed memory; written only by the memory analyzer)
- Per character: identity (traits, likes/dislikes, appearance description, speech style, backstory), behavioral patterns with confidence, a fuzzy current snapshot (mood, location, goal), directional relationships to other characters, and an observation log.
- World-level: running plot overview, locations, story arcs, unresolved threads.
- **Contains no mechanical fields** (no resources, skills, or inventory) — those are hard state.

## 8. Core modules

### 8.1 Mechanics Engine

Deterministic and fully unit-testable. Owns and is the sole writer of hard state.

- **Resolution:** uses a single d20 in the first release. For a contested or uncertain action, it rolls d20 + modifier against a difficulty value, computes the outcome, and owns the result. Resolution is honest: failures genuinely occur, the math is inspectable, and consequences are real.
- **Gating:** an action requiring a skill is permitted only if the character has learned that skill (and any prerequisites). Ungated attempts fail or carry a disproportionate cost; there are no dramatic exceptions.
- **Skill model (working design):** a skill's *unlock* is binary — a character has it or does not (this preserves the gating guarantee). A learned skill may additionally carry a **mastery rank** that supplies the d20 modifier and gates more advanced uses. (Binary-only is the simpler alternative; this is a design decision to confirm — see §14.)
- **Resources & inventory:** numeric resource ledgers and a structured inventory; item use may itself require a skill.
- **Multi-character:** hard state is per character. The protagonist and non-player characters can each have their own sheet; the engine manages all of them. Multi-character narration (one model voicing several characters) is a native, default capability, not a special case.

### 8.2 Memory & Continuity

Maintains soft state. Written by an **analyzer** — a (typically cheaper) LLM that reads each exchange and extracts narrative information. Soft state is allowed to be approximate.

- **Evolving character cards (from first release):** each tracked character has a card that visibly grows through play — current appearance/outlook, current status, what changed, key events, growth, plus identity and relationships. This is the primary user-visible "living" feature.
- **Character tiers:** primary characters are tracked in depth; secondary characters are auto-created with lighter tracking on first appearance and can be promoted.
- **Relationships:** directional and character-to-character (not only character-to-user).
- **World state:** plot overview, locations, arcs, unresolved threads.
- **First release scope — remembers, does not police.** Memory records and evolves but does not yet detect or correct narrative inconsistency. Automated drift detection is deferred. (Note: this refers only to *narrative* consistency. Mechanical enforcement via the engine is fully present from day one.)

### 8.3 Summarizer

The memory-compression mechanism, and effectively the same structured store as Memory & Continuity, presented as a document.

- **Tiered rollup:** raw messages are periodically compressed — every N messages into a "chapter," every M chapters into an "arc." Thresholds are configurable.
- **Per-chapter output:** a title and a summary of its message range.
- **Per-arc output:** a full structured extraction — plot summary, character development, relationship dynamics, key items, skills/powers, unresolved threads, timeline, and related sections.
- **Purpose:** the compressed summary is what gets injected into the model's context on each turn, keeping long stories within context limits without searching raw history. In the first release, the summarizer is the substitute for semantic search.
- **Relationship to Memory & Continuity:** the summarizer produces the structured compression; the evolving cards and world state are views of that same store. Build them as one system with multiple presentations.

### 8.4 Story Bootstrapper

Generates the Frozen Story Schema from a premise (or an imported character card), once, then freezes it.

- **First decision is stat mode** (`none` / `light` / `full`) — whether the story has mechanical stats at all.
- **Reliability across models:** uses constrained structured output (JSON schema / function calling) plus a **validate-and-repair loop** — generated output is validated against the expected schema, and on failure is sent back for repair up to a retry limit. A weaker model results in more repair attempts, not a broken story. Decision spaces are constrained with enumerations and caps so even modest models produce valid output.
- **No review for regular users:** the schema is generated, frozen silently, and play begins — no setup questionnaire. Advanced users can regenerate or edit the schema in settings. Regeneration is free before play begins; after play has started it must migrate existing progress or be locked, so learned skills and inventory are never orphaned.
- **Player-hidden, developer-visible:** the schema (skill prerequisites, difficulty values, unlock paths) is hidden from players to preserve discovery, but inspectable in a developer view for debugging.

### 8.5 Model Router & Access

- **Recommended path:** a single aggregator key (one account reaching many model providers through one OpenAI-compatible endpoint), introduced through a guided onboarding wizard.
- **Advanced path:** full provider exposure — the user may configure any supported provider (major hosted providers, an aggregator, or a custom OpenAI-compatible endpoint) and full sampler settings, comparable to power-user tooling.
- **Model tiering:** the application marks a tested "recommended" set distinct from an "advanced / variable results" set, so an underpowered model degrades prose quality but never mechanical integrity, and failures point at the model rather than the application.
- **Honest failure surfacing:** when generation fails validation after retries, the user is told plainly (e.g. "the selected model couldn't produce a valid setup — try a recommended model").

### 8.6 Persistence

- Embedded **SQLite**, structured, local.
- **No vector storage in the first release** (see §11).

## 9. Per-turn data flow

1. The player submits an action or message.
2. The core assembles context: the relevant parts of the frozen schema; current hard state for the player and any present characters; compressed memory (current arc summary, recent chapter summaries, relevant character/world soft state); recent raw messages; and any triggered lorebook entries.
3. If the action implies a mechanical resolution (attack, skill check, item use), the **mechanics engine evaluates it**: it checks gating (does the character have the required skill and prerequisites?) — denying or failing the action if not — and otherwise resolves it (d20 + modifier vs difficulty). The ruling is computed deterministically.
4. The ruling is supplied to the narrator model as authoritative context (inline in the request, which the application fully controls), and the narrator is asked to produce prose consistent with it.
5. The narrator returns prose. In the first release, prose is trusted for *flavor only* — the mechanical outcome was already decided in step 3, independent of what the prose says.
6. **State commits:** the mechanics engine writes hard-state changes (resource deltas, new items, newly learned skills) from its own ruling — never from the prose. Asynchronously, the analyzer extracts soft-state updates (mood, relationship shifts, observations) from the prose and writes them to the soft store.
7. **Periodic compression:** every N messages the summarizer produces a chapter; every M chapters it regenerates the arc-level structured extraction.
8. **Render:** the play screen shows the prose; the living card joins hard and soft state for display.

## 10. Model access strategy

- Users **bring their own model access** — their own key, their own balance, their own relationship with the provider. The application never becomes the customer of record and never sees content on a server.
- A guided wizard makes the recommended single-key path painless for newcomers: explain why a key is needed in plain terms, deep-link to signup, validate the key inline, and run a test generation so the first experience is success.
- Advanced users get full provider/model/sampler control.
- A free trial runs on the user's own key — it is a trial of the application's features, not free model usage.

## 11. Persistence and recall: why no vectors in v1

Semantic/vector search solves recall over large raw histories. The summarizer addresses this differently: by compressing history into a small, structured, injectable form (chapters and arcs plus structured soft state), recall is achieved by supplying the compressed memory directly, keyed by character/recency/arc. This avoids the weight and tuning cost of an embedding index. Vector search is deferred; if later needed for very long stories, it should index the *summaries*, not raw messages.

## 12. UI surfaces

1. **Setup wizard** — recommended single-key onboarding (guided), with an advanced branch exposing full provider and sampler configuration.
2. **Library / home** — the default screen after setup: bundled starter stories/cards plus the user's imported cards.
3. **Play screen + living card** — the chat, with a glanceable evolving character card available on demand (ambient, not a maintenance dashboard).
4. **Story overview (chapters & arcs)** — counts, a summarize action, and the per-chapter and per-arc structured summaries.
5. **Character card creator & editor** — create new cards and edit imported ones.
6. **Persona creator** — the user's own persona.
7. **Lorebook manager** — worldbook/lorebook entries.
8. **Advanced settings** — full model/provider/sampler control, schema regenerate/edit, summarizer thresholds.

## 13. Scope: first release vs later

**First release**
- Mechanics engine: d20 resolution, binary skill gating (with optional mastery), resources, inventory, multi-character hard state.
- Memory & Continuity: evolving cards, relationships, world state — remembers, does not police.
- Summarizer: chapter/arc rollup, structured extraction, context injection.
- Story bootstrapper: stat mode, structured-output generation with validate/repair, silent-freeze default, advanced regenerate/edit.
- Model router: guided single-key onboarding plus full provider exposure.
- UI: wizard, library, play + card, overview/chapters/arcs, card creator & editor, persona, lorebook, advanced settings.
- Import character cards, including import from a user-supplied URL where feasible.
- Licensing: free trial on the user's own key, then one-time purchase with paid upgrades.
- SQLite persistence.

**Later releases**
- Automated narrative drift detection and correction.
- Vector recall (over summaries) if needed.
- Additional dice types.
- Deeper schema editing and migration tooling.
- Mobile build.

## 14. Open design decisions

1. **Skill model (highest priority):** binary unlock only, or binary unlock plus a mastery rank that feeds the d20 modifier and gates advanced uses. The working design assumes the latter; confirm in the low-level plan, as it determines whether a skill is a flag or a small object.
2. **Modifier source for the d20:** mastery rank, attribute stats (only when stat mode is `full`), or a flat skill bonus. Tied to decision 1.
3. **Summarizer cadence:** the message-per-chapter and chapter-per-arc thresholds, and whether they are user-configurable.
4. **Product name** — to be decided.

## 15. Monetization and licensing (product context)

- One-time purchase with paid major-version upgrades; a free trial that runs on the user's own model key. Subscription is not used unless genuinely ongoing hosted value is later introduced.
- Licensing is handled by a third-party provider plus a lightweight validation check that never sees story content. There is no usage metering and no relayed inference.

## 16. Glossary

- **Core** — the non-UI program logic (engine, memory, bootstrapper, router, store).
- **Frozen Story Schema** — a story's rule set, generated once and read-only during play.
- **Hard state** — authoritative mechanical state (resources, skills, inventory); written only by the mechanics engine.
- **Soft state** — observed narrative state (personality, relationships, observations, world); written only by the memory analyzer.
- **Gate / gating** — the rule that a character can only perform actions their learned skills and state permit.
- **Bootstrapper** — the component that generates and freezes a story's schema.
- **Analyzer** — the LLM-driven process that extracts soft state from prose.
- **Narrator model** — the LLM that writes story prose; it does not own mechanics.
- **Chapter / Arc** — units of summarized history (a chapter compresses a block of messages; an arc compresses several chapters).
- **Stat mode** — whether a story uses no, light, or full mechanical stats.
