## 1. What the owner asked for

1. A few quests generated at story creation, "just to get things starting".
2. Full latitude on implementation, but document everything.
3. Quests range from specific to sweeping.
4. Difficulty tiers: **Light, Moderate, Hard, Brutal, Nightmare**. Nightmare is extremely rare and
   near-impossible, and is the route to a Mythical item.
5. **Use quests as an anti-drift device** — "with this we will never forget our goals, so inject it
   wherever need be".
6. On completion the player picks **one** reward from up to four: attribute upgrade, skill upgrade,
   tiered skill unlock, or an item — each tiered or locked by difficulty.

## 2. The authority question, settled first

A quest is a **contract about hard state**: completing it grants an attribute point, a skill rank, a
skill unlock, or an item. All four are hard state. Therefore:

- **Quest definitions** (title, description, objectives, difficulty, reward table) are hard state,
  authored at forge time or by an engine-owned generator, and **frozen** the same way the rulebook is.
- **Quest progress** (which objectives are met, status) is hard state, written **only by the ledger**
  in response to deterministic evidence.
- **Quest prose** (flavour text, the giver's dialogue) is soft.
- A model may **propose** a quest and may **narrate** its completion. A model may **never** mark a
  quest complete or choose a reward.

This is the single most important design decision in this plan. Get it wrong and the model can grant
itself a Mythical item.

### How completion is detected without a model deciding it

Objectives must be expressible as **deterministic predicates over engine state**:

```ts
type QuestObjective =
  | { kind: "defeat"; characterId?: string; templateId?: string; count: number }
  | { kind: "acquire_item"; itemDefinitionId?: string; itemKind?: ItemKind; count: number }
  | { kind: "reach_flag"; flagId: string }              // engine flags already exist
  | { kind: "learn_skill"; skillId: string }
  | { kind: "survive_turns"; turns: number }
  | { kind: "reach_location"; locationFlagId: string }
  | { kind: "narrative"; flagId: string };              // see below
```

The `narrative` kind is the escape hatch for sweeping quests ("end the war"): the objective completes
when an **engine flag** is set. The flag is set by an existing engine mechanism — an action's
`effects.setFlag`, which is already in `EffectSpecSchema` and is written by the ledger. So even a
story-shaped objective resolves through a deterministic write, never a model assertion.

- [ ] **2.1** Confirm `setFlag` is ledger-applied and checkpointed before relying on it.

## 3. Data model

```ts
// packages/core/src/types/quests.ts  (new)
export const QuestDifficultySchema = z.enum([
  "light", "moderate", "hard", "brutal", "nightmare",
]);

export const QuestRewardKindSchema = z.enum([
  "attribute_upgrade", "skill_upgrade", "skill_grant", "item",
]);
// NOTE: `skill_grant`, NOT `skill_unlock`. Per plan 09 §3.3, "unlock/enable" means a pool entry
// becomes available in the story's catalogue and a model may propose it; "grant/learn" means a
// character acquires it into hard state and ONLY the ledger may do it. A quest reward is a grant:
// the player chooses it explicitly and the ledger applies it. Using "unlock" here would blur the
// two authority rules that this whole design depends on.

export const QuestDefSchema = z.object({
  id: z.string(),
  storyId: z.string(),
  title: z.string(),
  summary: z.string(),
  difficulty: QuestDifficultySchema,
  objectives: z.array(QuestObjectiveSchema).min(1),
  /** Engine-computed at authoring time from difficulty. The player picks ONE at completion. */
  rewardOptions: z.array(QuestRewardOptionSchema).min(1).max(4),
  /** Optional gating so a quest only appears once the story has progressed. */
  availableWhen: z.array(ConditionSchema).default([]),
});

export const QuestStateSchema = z.object({
  questId: z.string(),
  status: z.enum(["available", "active", "completed", "failed", "expired"]),
  objectiveProgress: z.record(z.string(), z.number()),
  /** Set only when the player has chosen; the grant is applied by the ledger. */
  chosenRewardId: z.string().optional(),
  completedAtTurn: z.number().int().optional(),
});
```

### Reward tiering (owner decision D6)

Proposed table — the engine derives `rewardOptions` from `difficulty`, so a model cannot inflate it:

| Difficulty | Attribute | Skill upgrade | Skill **grant** | Item tier |
| --- | --- | --- | --- | --- |
| Light | — | — | — | common |
| Moderate | +1 | +1 rank | common tier | uncommon |
| Hard | +1 | +1 rank | uncommon tier | rare |
| Brutal | +2 | +2 ranks | rare tier | legendary |
| Nightmare | +3 | +2 ranks | epic/legendary tier | **mythical** |

A skill grant may only name a skill **already enabled in this story's catalogue** (plan 09 §3). A
quest can never pull an entry out of the universal pool as a side effect — enabling and granting stay
separate operations with separate authority.

This aligns with `equipment-loot.json`, which already gates `legendary` and `mythical` behind
`requiresMilestone: true` and `mythicalRequiresExplicitAuthorization: true`. **A completed Nightmare
quest is exactly the explicit authorization that field was waiting for** — reuse it rather than
adding a parallel gate.

- [ ] **3.1** Owner confirms the table.
- [ ] **3.2** Nightmare rarity must be enforced at *generation*, not hoped for: cap the number of
      Nightmare quests per story (proposed: at most one active at a time, and none before a
      progress threshold).

## 4. Persistence

New tables via migration (confirm the ladder head):

- `quests` — the frozen definitions.
- `quest_states` — per-quest progress.

Both need a typed repository (`packages/core/src/store/repositories/quests.ts`) — **all SQL lives in
repositories**, no exceptions. Quest state must be captured in the **turn checkpoint** so rewind
restores quest progress exactly, alongside hard state. Missing this breaks invariant 7.

- [ ] **4.1** Add quest state to `capture()` in `orchestrator/checkpoint.ts` and to the rollback path.
      Add an explicit test: complete a quest, rewind, quest is incomplete again and the reward is
      un-granted.

## 5. Generation (sub-point 1)

- [ ] **5.1** Add a forge phase (or extend Phase B) that emits 3–5 starting quests: one or two Light,
      one Moderate, one Hard. **No Brutal or Nightmare at creation.**
- [ ] **5.2** Every generated objective must validate against the frozen schema — a `defeat`
      objective must name a real template, an `acquire_item` a real item kind, a `learn_skill` a real
      skill. Invalid objectives are rejected and repaired, exactly as action validation works today.
- [ ] **5.3** Later quests may be proposed mid-story by a bounded structured call, validated the same
      way. Keep this **out of the first changeset** — starting quests only.

## 6. Anti-drift injection (sub-point 5) — the highest-value part

This is the sub-point most likely to improve the product, and the cheapest.

`orchestrator/context.ts` assembles the narrator context under a token budget with a fixed priority
order. Insert **active quest objectives** into that block, high priority, just below the rulings.

- [ ] **6.1** Add a compact active-quest section to the assembled context: title, one-line summary,
      and the *unmet* objectives only. Cap it hard (proposed: 3 quests, ~200 tokens) so it cannot
      crowd out rulings.
- [ ] **6.2** Also feed active quests into the **suggestion generator** (plan 11) so "Possible moves"
      can propose quest-advancing actions.
- [ ] **6.3** Do **not** inject quest text into the classifier prompt — it would bias classification
      toward quest actions and worsen finding 19.
- [ ] **6.4** Measure the drift improvement honestly, or do not claim it. Proposed: after N turns,
      count how many active-quest objectives were referenced in committed prose, before and after.

## 7. The reward moment

- [ ] **7.1** When every objective is met, the ledger marks the quest `completed` and the UI presents
      the reward options. **The grant happens only after the player chooses** — via a new bridge
      method `chooseQuestReward(questId, rewardId)` that validates the choice against the frozen
      `rewardOptions` and applies it through the ledger.
- [ ] **7.2** The choice is idempotent and single-shot: a second call for the same quest is refused.
      This is where a duplicate-grant bug would live; test it explicitly.
- [ ] **7.3** Bridge parity for the new methods (`listQuests`, `getQuest`, `chooseQuestReward`).
- [ ] **7.4** Reward-in-prose (sub-point 6.4, "effortlessly include this in prose"): pass the granted
      reward to the **next** turn's narrator context as a fact to acknowledge. It is a ruling-like
      fact, so it belongs in the authoritative facts block, not in free prose.

## 8. Implementation order

1. Types + repositories + migration + checkpoint integration (no UI, no generation).
2. Deterministic objective evaluation in the ledger.
3. Forge generation of starting quests.
4. Context injection (§6) — **ship this early; it is the cheapest win**.
5. Reward choice + grant.
6. UI (design deliverable).
7. Mid-story quest proposal.

## 9. Acceptance criteria

1. No model can mark a quest complete or grant a reward.
2. Objectives complete only from deterministic engine evidence.
3. Rewards are derived from difficulty by the engine; a Mythical item is reachable **only** through a
   completed Nightmare quest.
4. Quest state is checkpointed; rewind un-completes a quest and un-grants its reward exactly.
5. Choosing a reward is single-shot and idempotent.
6. Active quests appear in the narrator context under a hard token cap and never displace rulings.
7. New stories generate 3–5 starting quests, none Brutal or Nightmare.
8. Suite green; typecheck clean; both bridges expose the same quest surface.

## 10. Risks

- **Reward duplication** on retry/swipe/rewind is the most dangerous failure — it silently inflates
  the player's power. §7.2 and §4.1 are the guards; test them adversarially.
- **Scope.** This is the largest new feature in the set. The first changeset should be types +
  persistence + checkpoint only, with nothing user-visible, so the risky foundation is proven before
  any UI exists.
- **Objective expressiveness.** If the predicate kinds are too narrow, generated quests will be
  rejected constantly and the forge will stall. Measure the rejection rate during §5.
